# Spec: Deep audit of httpware — code + docs

**Date:** 2026-06-07
**Topic slug:** `deep-audit`
**Status:** drafted, awaiting user review
**Target output:** `planning/audit/2026-06-07-deep-audit.md` (triaged findings file)

## Purpose

Comprehensive multi-agent review of the httpware repository to surface bugs, concurrency hazards, contract violations, public-API drift, optional-extras boundary leaks, test gaps, and documentation/planning-doc inaccuracies. Produces a single triaged findings file under `planning/audit/`. The audit follows the recent 0.8.0 sync `Client` + `Async*` rename, where the surface area roughly doubled and several invariants are newly load-bearing.

The audit is read-only: it produces findings, not fixes. Fixes are a separate downstream effort.

## Non-goals

- **No fixes applied.** The audit reports only. Each finding includes evidence and a suggested direction, but no diffs land as part of this work.
- **No CI changes.** The audit does not introduce new lint rules, test files, or coverage thresholds. If a finding recommends one, it is recorded as such and acted on later.
- **No external research.** This is internal-code-and-docs only. No web search, no library docs fetched. Only the repo at `HEAD`.
- **No reformatting / no whitespace cleanup.** Style and formatting are tracked only when they cross into ambiguity that would mislead a reader.
- **No issue filing.** Findings stay in the file; converting them to GitHub issues is a separate downstream step the user controls.

## Architecture

The audit is structured as **four chunks**, each chunk a separate `Workflow` invocation. The user gates between chunks: review the appended section, then approve continuation, adjust scope, or stop.

```
┌──────────────────────────────────────────────────────────────────┐
│ Chunk 1: Code correctness  (Discover + dims 1, 2, 3)             │
│   ├─ Discover (Opus, one-shot)  → planning/audit/_discover.json  │
│   ├─ Find × 3 dimensions (Sonnet, parallel)                       │
│   ├─ Verify × 3 voters per finding (Sonnet, pipeline)             │
│   └─ Partial synthesis (Opus) → append to audit file              │
├──────────────────────────────────────────────────────────────────┤
│ Chunk 2: API & boundaries (dims 4, 5)                             │
│   Same shape; reuses _discover.json                               │
├──────────────────────────────────────────────────────────────────┤
│ Chunk 3: Tests (dim 6)                                            │
│   Same shape; reuses _discover.json                               │
├──────────────────────────────────────────────────────────────────┤
│ Chunk 4: Documentation (dims 7, 8)                                │
│   Same shape; reuses _discover.json                               │
├──────────────────────────────────────────────────────────────────┤
│ Final merge (Opus, one-shot)                                      │
│   Re-triage across chunks, rewrite summary header, commit         │
└──────────────────────────────────────────────────────────────────┘
```

### Why pipelined inside each chunk

Per Workflow guidance: a `pipeline()` over the dimensions lets each finding flow into verification as soon as its dimension finder returns, without waiting for slower dimensions to complete. Wall-clock = slowest single (find + verify) chain, not sum-of-stages. No barrier is needed inside a chunk because dedup is per-chunk against the existing file, not against all stage-1 outputs at once.

### Why chunked at the top level

Three reasons:

1. **Token budget control.** Each chunk's estimated consumption is ~500k–1.8M tokens. The user can pause if budget is tight or if findings warrant rethinking before continuing.
2. **Incremental value.** Findings file is committed after each chunk. Even if the audit stops at chunk 2, the chunks-1-and-2 findings are durable and reviewable.
3. **Adjustability between chunks.** After chunk 1, the user can drop a dimension from later chunks, raise the severity bar, or stop entirely. The cost of being wrong about scope is bounded to one chunk.

### Model assignment

| Stage                       | Model       | Why                                                                                                |
|-----------------------------|-------------|----------------------------------------------------------------------------------------------------|
| Discover (chunk 1 only)     | Opus 4.7    | One-shot; needs to produce a clean module map the finders depend on                                |
| Dimension finders           | Sonnet 4.6  | Structured lens-based review; output is JSON-schema-bound; quality difference vs Opus is small     |
| Verifiers (3 per finding)   | Sonnet 4.6  | Re-reads a small fragment; same quality argument                                                   |
| Partial synthesis           | Opus 4.7    | Triage decisions benefit from stronger judgment; small token cost                                  |
| Final merge                 | Opus 4.7    | Cross-chunk dedupe + summary rewrite; same                                                         |

## The 8 dimensions

Each dimension is a finder agent given:

- The discover output (module map + file list with line counts)
- `CLAUDE.md` (the architecture invariants)
- `planning/engineering.md` (the design reference)
- A dimension-specific prompt
- A `Finding[]` output schema

### 1. Correctness
Logic errors, off-by-ones, wrong branches, dead code, broken control flow, mis-named variables, accidentally-swapped arguments. Reads `src/httpware/` exhaustively.

### 2. Concurrency & sync/async parity
Race conditions, missing locks, behavior divergence between sync and async implementations of the same primitive. Cross-references `tests/test_*_props.py` against `RetryBudget`, `Bulkhead`, `AsyncBulkhead`, `Retry`, `AsyncRetry`. Special attention to: shared `RetryBudget` across sync `Client` + `AsyncClient` (new in 0.8.0), `threading.Semaphore` vs `asyncio.Semaphore` semantics, any `asyncio.timeout` removal fallout.

### 3. Error contract
Invariants from `CLAUDE.md`:
- Status-keyed errors take a single positional `response: httpx2.Response`
- Subclasses do not override `__init__`
- All fields available via `exc.response.*`
- 4xx/5xx mapping correctness in the terminal call

Cross-references `tests/test_errors.py` and `tests/test_error_mapping_terminal.py` against `src/httpware/errors.py`.

### 4. Public API surface
`src/httpware/__init__.py` exports vs `__all__`; typing in re-exports; missing/leaking symbols; stale `Async*` aliases or names left over from the rename; symbols re-exported from submodules that no longer exist or have moved. Cross-references `tests/test_public_api.py`.

### 5. Optional extras boundary
`pydantic`, `msgspec`, `otel` imports must be quarantined inside their dedicated modules and never touched at top-level import time. Fail-fast must trigger at `AsyncClient.__init__` / `Client.__init__` when the user requests a decoder whose extra is not installed, not at first use. Cross-references `tests/test_optional_extras_*` and `src/httpware/_internal/import_checker.py`.

### 6. Tests
Coverage gaps, fragile mocks, hypothesis property tests that don't prove what they claim (weak shrink targets, narrow strategies), sync/async parity gaps in the test files themselves (one world thoroughly covered, the other thin), mock transports that hide real httpx2 behavior, tests that pass for the wrong reason.

### 7. Docs accuracy
Every code block in `docs/*.md` must import and run against current code (especially after the sync rename — `Middleware` vs `AsyncMiddleware`, `Retry` vs `AsyncRetry`, decorator prefixes). Cross-references valid (links to symbols still exist, mkdocs nav matches reality). Recipes in `docs/recipes/` actually demonstrate what they claim.

### 8. Planning-doc accuracy
`planning/engineering.md`, `CLAUDE.md`, `README.md`, `planning/releases/0.8.0.md`, and `planning/deferred-work.md` against the actual repo state. Special attention: did the sync `Client` rename make any statement in `engineering.md` stale? Does `CLAUDE.md`'s module layout diagram still match `src/httpware/`?

## Schemas

### Finder output

```python
class Finding(TypedDict):
    dimension: Literal[
        "correctness",
        "concurrency",
        "error_contract",
        "public_api",
        "optional_extras",
        "tests",
        "docs",
        "planning_docs",
    ]
    title: str  # one-line summary
    file: str  # repo-relative path
    line_hint: int  # approximate line; not load-bearing
    claim: str  # 1-3 sentences of what's wrong + why
    evidence_quote: str  # 5-15 lines of the cited code, verbatim
    suspected_severity: Literal["blocker", "high", "medium", "low", "nit"]
    reproducer_hint: str | None  # how to demonstrate, if applicable


class FinderResult(TypedDict):
    findings: list[Finding]
```

### Verifier output

```python
class Verdict(TypedDict):
    lens: Literal["code_reality", "reproducer", "spec_grounded"]
    confirmed: bool
    reason: str  # 1-3 sentences citing evidence
    quoted_evidence: str | None  # short snippet supporting the verdict
    severity_adjustment: Literal["unchanged", "raise", "lower"] | None
```

A finding **survives** if ≥2 of 3 verifiers return `confirmed: true`. Default to lower severity if any verifier returns `severity_adjustment: "lower"`; raise only if ≥2 return `"raise"`.

### Three verifier lenses

- **`code_reality`** — re-read the cited lines (+/- 30 lines for context). Does the claim match what the code actually does, or did the finder misread?
- **`reproducer`** — would a test actually trigger the bug? Sketch the trigger in 3-5 lines. If you can't construct one, set `confirmed: false`. (For docs/planning findings, this lens reframes: "does the doc actually mislead a reader on a first reading?")
- **`spec_grounded`** — does this violate a stated invariant (CLAUDE.md, engineering.md, error contract, optional-extras pattern)? If yes, `confirmed: true` with strong reason. If it's a judgment call with no spec backing, allow `confirmed: false`.

## Severity bucket definitions

The user chose "everything triaged into buckets." To prevent the file from drowning in nits, the synthesis stage applies these definitions:

- **Blocker** — wrong-correctness bug that affects users in normal usage, OR a documented invariant violated, OR a doc example that does not run against current code.
- **High** — wrong-correctness bug behind a non-default code path; OR a missing safety check at a documented boundary; OR docs that mislead a reader making a reasonable choice.
- **Medium** — code that works today but relies on undocumented invariants; OR docs that are accurate but ambiguous; OR test gaps in load-bearing primitives.
- **Low** — minor inaccuracies, weak idioms, or hardening suggestions that improve robustness without fixing a current defect.
- **Nit** — style, naming, comment placement, doc punctuation. The file should have at most ~10 of these per chunk; if a finder produces more, the synthesis stage collapses them into a single rolled-up entry.

## Gate behavior between chunks

After each chunk completes:

1. The chunk synthesis writes its section to the audit file and commits with a message like `audit(chunk-1): code correctness findings`.
2. I report a one-paragraph summary to the user: `Chunk N complete. Found X total findings across the dimensions; A confirmed as blocker/high, B as medium/low, C as nit. Headline issues: <2-3 bullets>.`
3. The user decides: **continue / pause / adjust / stop**. "Adjust" means drop a dimension, change severity bar, or change models for the next chunk.
4. If continue, I launch the next chunk. Otherwise we stop and the report stands as-is.

## Final merge

After the user approves chunk 4 (or stops earlier), a final Opus agent:

- Reads the full `planning/audit/2026-06-07-deep-audit.md`
- Dedupes across chunks (same `file:line ±5` + similar claim → keep the higher-severity one, fold the other's evidence in)
- Rewrites the top-of-file summary header with final counts per bucket
- Adds a "Cross-cutting themes" section if patterns emerge across chunks (e.g., "three dimensions surfaced the same kind of missing-lock pattern")
- Commits as `audit(merge): final dedup and summary`

## Risks & mitigations

- **False positives drown the real bugs.** Mitigation: 2-of-3 verifier consensus required; verifiers explicitly told to default to "confirmed: false" when uncertain; nits get collapsed in synthesis.
- **Finders produce overlapping findings.** Mitigation: per-chunk dedup against the existing file; cross-chunk dedup in final merge; dimension prompts are sharpened to discourage cross-dimension overlap (e.g., "concurrency" explicitly excludes type-signature critique).
- **Docs lens claims doc is wrong when code is wrong.** Mitigation: when a `docs accuracy` finding is verified, the verifier must specify whether the fix is in the doc or in the code; if code, the finding is recategorized to its appropriate code dimension during synthesis.
- **Discover JSON drifts during the run if code changes.** Mitigation: the audit runs against `HEAD` at chunk-1 start; if the user pushes commits mid-audit, we stop and re-discover. Not expected in practice.
- **Verifier model misses subtle concurrency bugs.** Mitigation: for the `concurrency` dimension specifically, the synthesis stage flags any finding that survived with only 2/3 consensus for explicit user attention rather than collapsing it.
